4 Data flow, end to end

Teacher assigns work — Assign Games tab builds a dict per activity, save_assignments() appends it to assignments.json.
↓
Student opens the hub — who_key() lowercases the name; is_completed(class, activity) reads completions.json; finished games and fully-completed classes are hidden.
↓
Student plays — blank name is blocked. Each answer appends to st.session_state.answer_log (memory only, lost on refresh).
↓
Game finishes — a record is built and save_completions() writes it to completions.json. That is the only write from the student side.
↓
Teacher sees results — load_completions() is matched against assignments.json on (class, activity) to set each row's status.
Why the class is part of the match key: the same activity name can exist in several classes, and each counts as separate work. Matching on activity name alone would wrongly mark every class as done.

24 odd-one-out SVGs + images/odd_index.json.

Narrates the 24 passages to WAV + audio/index.json.

Builder

build_question_bank.py

Regenerates question_bank.js. Deterministic — same output every run.

Check

validate_bank.py

Whole-bank integrity: 325 keys, 975 questions, 4 options each, answer present, no duplicate stems, assets present.

Check

8 × check_*.py

Class filter, completion removal, name required, teacher status, odd one out, roles, teacher tab, instructions.

Caveat: the check_*.py scripts re-implement the app's conditions in isolation. They are not end-to-end UI tests — only a real browser pass confirms rendering.
